# ADR-034 — JPA engine for Flint

**Status** Accepted, 2026-11-26 (owner decision `0168bca6`).
**Reviewers** data-access for JDBC and transaction integration, flint-aot for generated metadata, accessors, proxies and JPQL.

## Context

[ADR-030](ADR-030-flint-is-a-spring-port.md) calls for a Hibernate-derived JPA engine with a persistence context, dirty checking, lazy loading, build-time JPQL and Criteria. Classic PetClinic is the first application after the engine. [Phase 1 data access](../spring/phase1/data-access.md) supplies the JDBC and transaction stack. [The AOT contract](../spring/aot-contract.md) supplies the build pipeline and descriptor conventions.

Jakarta Persistence 3.2.0 is the public contract. The API lives in `framework/jakarta-persistence` as `flint:jakarta-persistence`, with the Jakarta package names mapped to `flint.jakarta.persistence` and `flint.jakarta.persistence.criteria`. The API package has no provider, database, Spring, or engine dependency. Java vocabulary comes from `flint:java` where the [mapping rulebook](../spring/api-mapping.md) requires it. API source ports use the BSD-3-Clause option in the [3.2.0 source tag](https://github.com/jakartaee/persistence/tree/320bface63284bf72f5844dc34f6b8ddad7b39c7), and retain each file's notices. Check license eligibility separately for TCK source. Where no eligible API test exists, write original tests against the [3.2 contract](https://jakarta.ee/specifications/persistence/3.2/) and report them as Flint tests.

## Decision

Propose `framework/engine-jpa` for the provider and private engine, with Spring ORM integration above it. Applications receive Jakarta interfaces and GC-owned values. The provider translates engine status to Jakarta exceptions at the API boundary. Hot engine routines are `@safe nothrow @nogc`, use bounded storage, and return `Result`. Repository and Boot integration consume the Jakarta contracts. They stay outside the engine and follow separate slices.

Use Hibernate ORM [7.1.0 at 02eb1ac3](https://github.com/hibernate/hibernate-orm/tree/02eb1ac3e09b28a954b530c607357b6495ce5957) as the proposed reproducible source pin from the Apache-licensed ORM lineage. This release descends from the [HHH-19191 relicensing commit](https://github.com/hibernate/hibernate-orm/commit/aa06c7f). Review the pin before porting, verify the license header for every derived file and test, and record its path and commit. The upstream `main` branch is a design reference. Use the following algorithms and their applicable tests from the pinned release.

| Concern | Hibernate source area | D implementation |
| --- | --- | --- |
| Managed identity and lifecycle | `engine/internal/StatefulPersistenceContext`, `engine/spi/EntityKey`, `engine/spi/Status` | One identity per root entity mapping and canonical primary key within a context. Track lifecycle in engine structs. Repeated loads and reloads through associations resolve the same managed instance. |
| Dirty checking, cascades and flush | `event/internal/DefaultFlushEntityEventListener`, `engine/spi/ActionQueue`, `engine/internal/Cascade` | Compare mapped values with loaded snapshots, including mutable values through generated copy/equality operations. Order inserts, updates and deletes by dependency and stable action order. Use version predicates and validated row counts for mapped optimistic locks. |
| JPQL and Criteria | `query/hql`, `query/sqm`, `query/sqm/sql`, `sql/ast` | Port the semantic resolution and SQL lowering needed by the supported JPQL and Criteria features. Use a shared typed query representation and emit dialect SQL plus parameter and result bindings. |

The initial provider supports resource-local CRUD, generated identifiers, versioned updates, mapped superclass attributes, to-one and to-many associations, cascades and lazy fetch, plus typed JPQL and Criteria for the classic PetClinic queries. Derive the precise mappings and query forms from the pinned classic application before implementation. Cover entity lifecycle and Criteria independently of the app. Support pinned PostgreSQL first. Admit another dialect only once its behavior and transaction tests pass.

### Generated mapping and query plans

Flint AOT reads declared entities, relationships, callbacks and named queries from the build closure. It emits immutable mapping tables, constructor and accessor thunks, and lazy proxy classes at build time. Use stable descriptor identity and field ordinals. Keep the generated thunks small and call a shared engine. Validate mappings, unresolved associations, inaccessible accessors, and unsupported proxy shapes with source locations. A lazy to-one proxy requires an interceptable property or method. A direct field read cannot trigger a load. Reject a mapping that requires an interception Flint cannot provide, or use eager loading where allowed by the mapping. A to-many uses a typed collection façade and records loaded state separately from empty contents.

Compile named JPQL and statically known JPQL call sites in Flint AOT. Resolve entity paths, joins, parameter types and projection shape against the generated mappings. Emit SQL and a binding plan for the configured dialect, including one bind slot per scalar occurrence. Any documented collection expansion works from typed bind slots and never interpolates values into SQL. Reject unsupported syntax or unbound runtime JPQL strings with an explicit diagnostic. For runtime Criteria, build an explicit typed tree through the Criteria API and lower it with the same semantic and SQL rules. User-visible Criteria nodes may allocate as allowed by the API. Cache only immutable plans with owned keys and no parameter values, and prove cold and cache-hit paths separately if a cache is introduced.

### Memory and transactions

Entity objects, proxy façades and values visible to user code are GC-owned. A persistence context keeps managed instances in GC-scanned storage. Arena tables hold only slot IDs, scalar and byte snapshots, engine state, and work buffers. They contain no GC references. Generated accessors and lifecycle callbacks that can throw or allocate run at the API boundary. A row consumer copies or materializes only what must survive cursor advancement. The context leases an arena with a context lifetime. JDBC call scratch has its own shorter lifetime. Closing or clearing a context invalidates its lazy handle generation before slots can be reused. A detached object keeps initialized values. Access to a still-unloaded association after detach fails without reattaching or opening a connection. The engine retains a lease and buffers until cancellation or I/O reaches terminal completion.

An application-managed `EntityManager` owns its context and has single-fiber use. A Spring-managed transactional façade resolves the bound context through `TransactionSynchronizationManager` and its `FiberLocal` state. Coordinate with data-access on the integration that gives JPA and `JdbcTemplate` one transaction-bound connection, one owner for acquisition and close, and one commit or rollback. Reuse the existing JDBC driver, SQL engine and pinned PostgreSQL peer. Preserve rollback-only state. Flush on commit and at the required AUTO query boundaries. A flush failure stops subsequent flush actions and marks the transaction rollback-only. Rollback and close detach or retire affected state so reuse cannot publish rolled-back changes. `REQUIRES_NEW` suspends both the holder and persistence context and restores them on completion. Defer nested JPA propagation until savepoint rollback can reconcile tracked state with the database. Prove cleanup, two interleaved fibers, re-entrant and stale proxy access, JDBC visibility, and failure and cancellation during a flush on the real peer.

### Performance acceptance

This ADR proposes the following JPA-specific limits for owner approval. It leaves existing release goals and the certified petclinic-rest JDBC workload intact.

- **Parity first.** Compare an opt-in JPA-backed petclinic-rest variant with the pinned `JdbcTemplate` version using the same app shape, dataset, PostgreSQL and pool settings, compiler and link mode, HTTP/TLS setup and load schedule. Both must pass all applicable exact-response and database-state checks. For the paired performance paths, capture SQL, parameters, result rows and transaction boundaries, and match the JDBC work. Exercise reads (including the existing owner lookup and required associations), writes, and errors. Record distinct lazy-load and flush workloads with their SQL counts. Work with proof-harness on equivalent fixtures before scoring. Any change to a certified workload needs a separate owner decision.
- **Proposed per-path limits.** Zero GC allocations for engine bookkeeping. The JPA variant may allocate GC objects required by the API and visible entity graph, with a measured count and byte cap recorded per case before landing. On matched work, at most 1.05× the JDBC instruction count and p99 latency, and at least 0.95× its throughput. Preserve existing Go-relative and per-endpoint gates. Queue comparative timing through proof-harness. Store base and candidate commits, native and compiler identities, binary and workload digests, SQL traces, and raw samples.
- **Build and size.** Reuse generated descriptors and shared non-template engine functions. Emit one static plan per distinct query and keep engine and provider objects out of JDBC-only links. Set and gate the new packages' linked-byte and template-instance caps using the existing corrected probe method. Record cold and edit builds under the same toolchain and dependency closure, and keep timed certification with proof-harness.

## Exclusions and landing order

Phase 2 excludes JVM reflection and runtime bytecode, Hibernate-specific public APIs and HQL extensions, schema generation and migration tooling, JTA/XA, distributed and second-level caches, reactive sessions, and implicit open-session-in-view. Defer XML bootstrap/mappings, arbitrary runtime JPQL, stored procedures, and unsupported mappings or Criteria features outside the first application. Report the exact omitted elements and reasons in the API and test inventories. The provider must fail unsupported operations explicitly.

1. Port the eligible Jakarta API surface and its independent tests while this proposal is reviewed.
2. After owner approval, agree the shared JDBC, transaction and AOT contracts with their reviewers. Verify entity identity, materialization, detach, commit/rollback and optimistic locking on real PostgreSQL.
3. Add lazy relationships, cascades and generated JPQL. Verify diagnostic, parameter binding, load count and transaction semantics. Add Criteria against the same lowering and provider.
4. Run classic PetClinic acceptance and the petclinic-rest comparison. Retain the current JDBC path as the baseline. Pass the module definition-of-done checks, the porting playbook checks and applicable app budgets before integration.
