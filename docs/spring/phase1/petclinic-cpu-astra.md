# PetClinic owner-1 CPU plan

**Below 55 µs of application CPU per request is plausible, but it is a stretch target.** I would plan around **55–65 µs for a specialized, Spring-faithful path** and treat **45–55 µs as the range to test with a minimal reference handler**. Neither is a measured Flint floor. The strongest reason to pursue 55 is in B2’s raw trials. With the same transaction and SQL, Go used **63.3 µs at the scored 5,000 req/s and 55.5 µs at capacity**. Flint used **99.9 and 104.0 µs**, respectively. That makes 55 credible for the underlying work while leaving a real question about Flint’s cost for fibers, JDBC and the user-visible object graph. [B2 raw trials](../../../benchmarks/spring/evidence/phase1-http-petclinic/20261124T125955Z/http.json)

The goals have different budgets. Against B2’s Go median, the CPU gate corresponds to about **62.7 µs** before allowing for the 99% confidence interval. Reaching 55 requires saving **44.9 µs**. The internal throughput goal is now **26,078 req/s** (`1.30 × 20,060`). At that rate, each two-CPU tier has **76.7 µs/request** available, and ten connections allow at most **383 µs mean lease hold**. At fixed rate, closing the p50 gap requires recovering about **243 µs of elapsed time**. Even a 45 µs CPU saving leaves substantial socket, dispatch or wake delay to explain. [B2 decisions](../../../docs/spring/phase1/decisions.md)

**First establish the floor.** Use the already approved `floor-reference` diagnostic in the next available measurement window. Run three arms at the same revision: ordinary Flint, a minimal handler on the same fiber/HTTP stack with pinned libpq and identical response bytes, and that handler with the real owner/pet/type mapping, DTO construction and Jackson writer restored. All three must read the database on every request, through ten connections, with `BEGIN READ ONLY`, the three SELECTs and `COMMIT`. At 5,000 req/s and at capacity, record application and PostgreSQL CPU separately, plus lease wait/hold, socket wait and ready-to-resume delay. The middle-to-last difference prices the object and serialization work that a shippable path must retain. If the minimal arm already exceeds 55, prioritize transport and database driving before funding broader generation. It identifies work worth removing. It cannot price kernel time, contention at 64 connections or GC pauses in the scored run. The ranges overlap wherever two changes eliminate the same allocation, copy or collection.

## What would justify a larger change

**Use 100 allocations/request as the first engineering target and 60–80 as a stretch target**, then revise against the measured count of user-visible objects. Owner 1 measured **235 allocations at `6200b84b`**, before the latest row changes. The suite’s owner 6 has a different graph. Recount owner 1 at `09c0bb6a`, including bytes by caller and retained bytes under concurrency. An allocation saved from a six-row query has a different value from a small wrapper saved once. [Owner-1 census](/home/olfa/flint-work/coordination/inbox/coordinator.md:1044)

The best structural candidate is a **shared JDBC executor for known bind and row shapes**. Generate compact metadata, verify the actual driver, columns, types, mapper and configured conversions, then decode through scoped engine storage into the final GC-owned objects. Keep custom mappers, extractors and dynamic SQL on the ordinary JDBC path. Preserve setter side effects, SQL NULL, conversion errors and cancellation/drain before lease reuse. Building an entire arena graph and copying it at the controller boundary would retain two representations and expose lifetime problems wherever a mapper or setter retains a value.

I would **not budget a 30–40 µs win from that executor alone**. JDBC, engine-JDBC and engine-SQL together account for about 64k of 564k direct instructions, and the profile’s entire GC share is 22%. A larger win requires removing work across both categories *and* finding loaded costs the serial trace misses. The recent 2.6% and 1.7% reductions were worthwhile, independently testable instruction savings. Their value now is to test components of the larger design. Extrapolating them into certified microseconds would overstate progress.
