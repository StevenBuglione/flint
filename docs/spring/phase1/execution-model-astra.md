# Keep Flint’s fibers. Make fewer requests need them.

Flint already has the useful part of native virtual threads. A developer can write a blocking `JdbcTemplate` call, retain transaction and security context across it, and let the reactor serve another request while PostgreSQL works. A different stack representation can make suspension cheaper. It cannot wake a lease holder that nobody notified, reduce PostgreSQL’s CPU demand, or remove a single row conversion.

**Keep the stackful fiber as the general execution model.** Finish the targeted lease wake. Then invest in two capabilities that can distinguish Flint: use its knowledge of Spring configuration to execute proven short requests directly on their owner, and use its knowledge of JDBC bindings and result shapes to remove repeated work across the D/libpq boundary. The combination is a credible advantage for a Spring-compatible native runtime. There is no evidence for a scheduler that would give Flint a universal performance lead. [ADR-030 §4](../../../docs/adr/ADR-030-flint-is-a-spring-port.md:97) · [OpenJDK’s rationale for virtual threads](https://cr.openjdk.org/~rpressler/loom/loom/sol1_part1.html)

## What the numbers require

**PetClinic has three independent ceilings.** At 1.30 × 28,300, the target is 36,790 completed owner lookups per second. The benchmark gives the application two CPUs, PostgreSQL two *other* CPUs, and the pool ten connections. Assuming one lease per successful request, the following are saturation limits. A healthy p99 needs headroom below them. [Benchmark manifest](../../../policy/spring-http-benchmark.json) · [Earlier throughput plan](../../../docs/spring/phase1/throughput-plan-astra.md:60)

| Resource | Allowance at target | What today’s figures imply |
|---|---:|---|
| Flint application CPU | 54.4 µs/request | If the local 100 µs serial cost persists under load, the ceiling is 20k req/s. About 46 µs must come out. |
| PostgreSQL CPU | 54.4 µs/request | If the reported 104 µs persists, the ceiling is 19.2k req/s, even with a free application tier. At target it would require 3.83 database CPUs. Go’s reported 14 µs makes this discrepancy worth investigating immediately. |
| Time occupying a lease | 272 µs/request on average | Includes database waits, application work done while holding the lease, and transaction completion. A free lease stranded behind a sleeping waiter wastes additional capacity. |

The first failure was a **5.1 ms CPU spin**. Waking the fiber on socket readiness brought the serial diagnostic to **0.10 ms CPU and 0.25 ms wall**. The next failure is visible in two short pieces of code. `flint_sql_pool_acquire` admits only the FIFO head when callers are queued, and `pauseForLease` puts that head to sleep for 1 ms. Rechecking every loop pass moved the local result from roughly **1.5k to 9–17k req/s**. That establishes the importance of handoff latency. It gives neither a production implementation nor a certified forecast. [SQL wait](../../../packages/engine-sql/source/flint/engine/sql/sys/wait.d:88) · [FIFO acquisition](../../../packages/engine-sql/native/ffi/flint_sql_core.c:157)

We do not yet have an honest breakdown of the 100 µs. On the actual `/owners/1` route, measure application CPU separately for HTTP admission/dispatch, transaction and lease bookkeeping, libpq drive, row mapping, and JSON/send. Timestamp release→wake→acquire and acquisition→return as wall time. On the database CPUs, divide backend CPU by successful requests over the same interval for both implementations. Count actual statements, transactions, prepares, executions, rows and connections opened after warm-up. Flint’s lazy read-only `BEGIN` and `COMMIT` add two commands to the three reads. They do not by themselves establish the cause of a 7.4× CPU difference. Also, the familiar **360 allocations / 34 KB** measurement is for **owner 6**. Owner 1 has one pet and no visits. [JDBC transaction entry](../../../framework/engine-jdbc/source/flint/engine/jdbc/package.d:393) · [Owner fixture distinction](../../../docs/spring/phase1/throughput-plan-astra.md:71)

**gs-rest has a different problem.** Certified throughput is 319.3k against 249.5k, about **5.1k req/s** short of 1.30× at the Go median. But p50 needs to fall from **69 µs to about 60 µs**, and peak RSS from **19.6 MB to about 13.8 MB**. p99 already passes at 0.826×. CPU/request is 0.951× at the median, but its upper 99% bound is 1.029. Measure arrival→handler start→first write→completion at the fixed latency rate. An eight-microsecond queue delay and eight microseconds of CPU demand call for different changes. [Certified B results](../../../docs/spring/phase1/decisions.md:558)

## Execution models and one-day decisions

**1. Keep owner-local fibers and wake the eligible waiter directly.** Finish the reserved per-slot record, ready bitmap, wait generation and coalesced owner `eventfd`. Register and recheck eligibility before parking. Publish the available lease before signalling. Only the owner resumes the task. Wire cancellation, withdrawal and final native retirement into head advancement. An ordinary `post` can deadlock progress because `processMessages` stops when all fibers are occupied. This is the largest near-term PetClinic capacity and queue-latency opportunity. Expect p50/p99 gains under contention, little RSS change, and lower CPU than continuous polling. **Day test:** ten leases, two owners, mixed fiber/thread waiters, all task slots occupied. Race release against park, timeout and slot reuse on epoll and io_uring. Require FIFO progress, disappearance of the 1 ms handoff mode and completion of the unchanged 5k req/s warm-up. [Reactor mailbox admission](../../../packages/engine-reactor/source/flint/engine/reactor/package.d:1478) · [Wake design](../../../docs/spring/phase1/throughput-plan-astra.md)

**2. Execute a proven short handler directly on its owner.** This is the first compiler/runtime experiment I would fund. Today `engine-web` posts even a same-owner HTTP/1 request, and the servlet fast offer runs *inside* the fiber. Extend AOT’s existing shape check and startup proof to cover suspension, blocking, bounded work and the actual configured call targets. For eligible requests, enter a logical task context on the owner, preserve handler admission and fairness, invoke the controller once, serialize into transport-owned storage and let completion finish a partial send. Unknown virtual calls, native callbacks, hooks and unbounded user work select the fiber before invocation. Off-fiber `FiberLocal` currently falls back to thread-local storage, so installing and clearing a real task context is essential. A shipping fiberless path also needs an explicit amendment to ADR-030’s every-handler rule. [HTTP admission](../../../packages/engine-web/source/flint/engine/web/runtime.d:992) · [Servlet fast offer](../../../framework/engine-servlet/source/flint/engine/servlet/fast.d:40) · [Task-local storage](../../../packages/engine-reactor/source/flint/engine/reactor/package.d:125)

**Day test:** hand-specialize the real greeting path as a diagnostic before building compiler analysis. Preserve the counter increment, owned `name` string, Jackson bytes, and backpressure. Compare existing dispatch, owner-local fiber dispatch, and direct execution. Count entries, resumptions, allocations and queue delay. A roughly 1.6% capacity improvement would close the *median* throughput gap. The stronger reason to pursue it is a repeatable fixed-rate p50 and CPU improvement with p99 intact. Expect little immediate RSS benefit while the fiber pool remains provisioned. “Zero allocation” is a legitimate target for framework overhead only where ownership permits it. The existing fast path already demonstrated **1.394× on/off throughput** with essentially identical RSS. [Fast-path evidence](../../../docs/spring/phase1/fast-path.md)

**3. Generate stackless continuations at known waits.** A compiler-fork analysis could identify transitive suspension points and emit ordinary D frames containing a resume state, live values and cleanup state. The reactor would resume the frame on its owner. This can save stack pages and switch CPU for routes that actually suspend. Database service time remains, and larger continuation frames or extra allocation can worsen CPU and p99. **Day test:** hand-lower one real transaction sequence. Compare CPU, touched bytes and latency with pooled fibers under identical waits. Force cancellation and exceptions at every suspension, including rollback and `finally`. Even eliminating 5 µs from a 100 µs application path buys only about 5% application capacity. Pursue compiler work only if the measured saving justifies it. Body-dependent proofs must invalidate on callee-body changes and produce the same behavior in DMD and LDC builds.

**4. Borrow a stack, promote on block, or copy Loom-style stack chunks.** Promotion is practical at a generated boundary with an explicit continuation. Arbitrary promotion halfway down a native D call chain is a compiler, ABI and druntime project. A `ref` into a caller’s stack, an outstanding C borrow, exception unwinding and conservative GC roots all constrain relocation. Replaying a controller after it blocks duplicates visible effects. Flint already reserves guarded 256 KiB stacks and discards initially touched pages on supported platforms. Reserved address space greatly overstates reclaimable RSS. **Day test:** census resident stack pages, live depth and first-block frequency at 64 connections. Measure copy/restore cost for those depths and test an address-taken local across a yield. The possible RSS win is bounded by resident stack pages. Copying adds CPU and can lengthen both latency percentiles. Keep stable stacks for opaque frames. [PoolFiber implementation](../../../packages/engine-reactor/source/flint/engine/reactor/sys/fibers.d:11)

**5. Prefer core-local connections. Introduce stealing only for demonstrated imbalance.** Give an eligible FIFO ticket an idle same-owner PostgreSQL connection when possible, retaining the global ten-slot limit, cross-owner handoff and exclusive ownership through commit or drain. This could reduce cache traffic, foreign wakes and CPU/request without growing RSS. A rigid five/five split can strand capacity and worsen p99. Stealing a live task also carries transaction, socket and `FiberLocal` ownership costs. **Day test:** replay balanced and skewed arrivals after fixing handoff. Count busy time by owner, idle leases with waiters, remote wakes and p50/p99. If imbalance costs capacity, try assigning *unstarted* work before considering migration. Keep bounded offload for blocking C work such as SQLite and BCrypt. [Seastar’s sharding model](https://docs.seastar.io/master/group__smp-module.html)

**6. Specialize the JDBC data path and pipeline only proven command sequences.** This is the second investment. The PostgreSQL shim allocates five parameter arrays even on a prepared hit. Row metadata and cell copies repeatedly enter a process-wide mutex. Use bounded inline bind storage, one generation-validated row visit, and immutable mapping plans for known result shapes. Keep user-visible values owned, honor custom mappers and fall back on shape mismatch. **Day test:** use owner 1 to count allocations, mutex entries, copied bytes and CPU by layer. Prototype the largest site. These changes can reduce application CPU, both latency percentiles and allocation pressure. They cannot explain away backend CPU. SIMD deserves a separate trial only if decoding occupies measurable CPU on these short rows. [libpq bind path](../../../packages/engine-sql/native/ffi/flint_sql_pg.c:392) · [Row access](../../../packages/engine-sql/native/ffi/flint_sql_core.c:661)

For round trips, prototype the existing lazy `BEGIN` and the known first extended query in one pinned-libpq pipeline on one lease. Preserve isolation, first-error attribution, result order, rollback and drain through sync. Keep commit behind successful application processing. Different requests cannot share one open transaction, and batching identical owner reads would change the workload. **Day test:** compare flushes, waits, backend CPU and lease hold time, including failed `BEGIN`, failed query and cancellation. Saving one wait can move the 272 µs lease budget and both latency percentiles. Throughput rises only while lease occupancy limits it. Bound pipeline buffers and measure RSS. [PostgreSQL pipeline semantics](https://www.postgresql.org/docs/current/libpq-pipeline-mode.html)

**7. Use io_uring features where a counter shows removable work.** Flint already tries `DEFER_TASKRUN`; prior ring-flag experiments produced no certified throughput gain. Multishot accept has little leverage on 64 persistent connections. Multishot receive and provided-buffer rings could amortize receive submissions. Registered buffers cost resident memory. Linked SQEs help when operations are known together. `SQPOLL` consumes CPU that must be charged to the experiment. Zero-copy send adds buffer-lifetime tracking for responses of just 34–48 or 233–234 bytes. **Day test:** count enters, SQEs/CQEs, copies, short writes and completion→handler delay on both backends. Try one feature against the dominant count. Expect little movement on these bodies absent contrary evidence. Verify fallback and hold buffers until final kernel notification. [Reactor shim](../../../packages/engine-reactor/native/ffi/flint_reactor_uring.c:55) · [liburing send completion contract](https://github.com/axboe/liburing/blob/master/man/io_uring_prep_send_zc.3)

**8. Use regions for proven private lifetimes and measure GC pool policy separately.** Apply escape analysis to framework scratch. Keep DTOs, strings and anything retained by user code independently owned. A request boundary cannot collect arbitrary D references stored in a singleton or passed to another thread. **Day test:** run the planned fast-path pool A/B with allocation counts, resident mappings, live bytes and pause histograms. An earlier small-pool arm saved about **4.4 MB** at a **2.1% throughput cost**; repeat on the shipping fast path. Affinity-aware marking already ships. The concurrent collector prototype worsened local throughput and p99. This gives RSS a credible experiment without betting the application on a new collector. [GC diagnosis](../../../docs/spring/phase1/gc.md) · [Certified pool experiment](../../../docs/spring/phase1/decisions.md:523)

## Order of investment

1. **Finish wake and FIFO handoff.** In parallel, reconcile PostgreSQL CPU and complete the owner-1 profile. The first acceptance result is an available lease reaching its eligible waiter promptly under saturation.
2. **Cut the measured SQL costs on both CPU budgets.** Start with bind and row processing on the application side. Let backend statement counts, prepare rates and execution profiles select the database-side change. Pipeline only when a measured wait justifies it.
3. **Run the direct-owner greeting experiment and the RSS pool experiment separately.** Keep the existing single-pass binding work. A direct path can replace the mailbox hop and fiber entry for qualifying routes. It makes a universal stack-copying runtime unnecessary for that win. Retain fibers, targeted wakes and bounded offload for the rest.

This assessment uses checkout `33df8c3d` and the supplied measurements. The one-day experiments are proposals. Promotion should require byte-exact behavior, cancellation and overload tests, `@safe` boundaries and `nothrow @nogc` engine hot paths. Certify each change against the unchanged Go comparator and workloads, including TLS, with the 99% bounds. For generated paths, also gate cold and edit builds, stripped size, and generated-code budgets. A faster request that makes every Spring application slower to build would miss Flint’s objective.
